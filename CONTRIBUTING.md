# Contributing to Runnix

Thanks for picking this up. Runnix is a multi-tenant sandboxed code-execution
platform (Go services, NATS JetStream, Postgres, gVisor sandboxes). This guide
gets you from zero to a passing PR.

## Prerequisites

- Go 1.26+, `just`, `sqlc`, Docker with the `runsc` (gVisor) runtime
- `golangci-lint` v2 (CI pins v2.13.2) for `just lint`

## Local setup

```bash
just compose-up          # postgres:16 + nats:2 + gateway/dispatcher (+ runner image build)
curl localhost:4000/healthz
curl localhost:4000/languages   # currently ["python"]
```

Register, submit, poll (full walkthrough in `README.md` Quickstart).
To stop everything — this **drops the database volume**:

```bash
just compose-down
```

No `.env` file needed for the laptop stack (dev values are baked into
`deploy/compose.yaml`). Hosted dev/prod stacks use `deploy/*.env.example`
templates — those files are never committed; see `deploy/README.md`.

Prefer running one service against compose infra? Start the stack, then:

```bash
just dev           # gateway on :4000 (expects Postgres + NATS reachable)
just dispatcher    # dispatcher (needs Docker socket + Postgres + NATS)
```

## Development loop

```bash
just test        # full suite with -race (unit + testcontainers integration)
just vet         # go vet ./...
just lint        # golangci-lint
just build       # binaries to dist/ (gitignored, don't commit)
just generate    # regenerate sqlc code after touching queries/ or migrations
just migrate-up  # apply migrations to a standalone DB (compose auto-migrates)
```

Integration tests boot real Postgres/NATS containers and run real code in the
sandbox; they skip automatically when Docker is unavailable. If NATS behaves
oddly locally, note the monitor port (8222) can reset connections — verify
stream state from the app side instead.

Check available recipes any time: `just --list`.

## Where things live

- `cmd/gateway` — stateless HTTP API (auth, tenancy, JetStream publish)
- `cmd/dispatcher` — JetStream consumer, sandbox runs, result writer, webhooks, reaper
- `internal/store/migrations/` + `queries/` — schema and SQL (source of truth)
- `internal/store/storedb/` — **generated by sqlc, never edit by hand**
- `api/openapi.yaml` — the API contract; `docs/` — webhook + parity notes
- `runner/docker/` — sandbox image; `deploy/` — compose stacks + runbook

## Making changes

1. **Storage:** add a new `internal/store/migrations/NNNN_*.sql` (embedded,
   must apply idempotently and be replica-safe), update `queries/*.sql`,
   then run `just generate`. Never edit `storedb/` directly.
2. **API:** update `api/openapi.yaml`, the handler, and `docs/` in the same
   commit so the contract never drifts from the code.
3. **Tests:** add/extend `*_test.go` next to the code you touch
   (`TestAPIKeyFormat` in `internal/auth` is a good small example).
   Full suite must pass with `-race`.
4. **Changelog:** user-facing changes get a `CHANGELOG.md` entry
   (Keep a Changelog format). Internal chores don't.
5. **Security-sensitive areas** (sandbox flags, SSRF guard, webhook signing,
   auth middleware): don't weaken defaults. `WEBHOOK_ALLOW_PRIVATE` stays
   dev-only; sandbox stays non-root, no network, read-only rootfs.

House rules: no `phase` wording in commits/code (use `deferred: <topic>`
tags for follow-ups); error responses stay `{"error": "..."}`; cross-tenant
reads return `404`, never leak.

## Commits and PRs

- Message style: `<prefix>: <subject>` — e.g. `feat: …`, `fix: …`,
  `docs: …`, `chore: …`, `ci: …`.
- Sign off and GPG-sign every commit: `git commit -s -S`.
- Keep PRs focused; describe behavior change + how you verified
  (`just test`, compose round trip, or both).
- CI must be green: vet + race tests + lint + build (`ci.yml`), plus image
  builds (`docker.yml`, no push from PRs).

## Releases (maintainers)

Releases are tag-driven: push `vX.Y.Z`, and `release.yml` gates on
vet/test/build, publishes linux amd64/arm64 binaries with checksums, and
derives notes from the matching `CHANGELOG.md` section. Images get version
tags plus `latest`; `main` continuously ships `edge` for the hosted dev stack.
